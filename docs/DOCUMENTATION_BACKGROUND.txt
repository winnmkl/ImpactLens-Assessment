1. EXECUTIVE SUMMARY
================================================================================

ImpactLens is a web-based Information Security Risk Assessment (IAR) application
built for PLM's ISMS. It supports multi-role collaboration (Standard User, Info Sec,
Admin/CISO), a three-tier asset approval workflow, standards-aligned risk
calculations, thirteen mapped security controls, mandatory compliance floors, and
multi-sheet Excel audit exports.

The system implements the NIST SP 800-30 Rev. 1 risk assessment lifecycle, maps
controls to NIST CSF 2.0, ISO/IEC 27001:2022, CIS Controls v8, SOC 2 TSC, and
PCI-DSS v4.0, and applies Philippine Data Privacy Act (RA 10173) baselines where
PII or SPI is processed.

Backend: Supabase (PostgreSQL, Auth, Row Level Security).
Frontend: Vanilla JavaScript, HTML, CSS (no React, Angular, or Vue).

2. SYSTEM OVERVIEW AND ARCHITECTURE
================================================================================

2.1 High-level architecture

  Browser (user)
       |
       |  HTTPS + JWT (Supabase Auth)
       v
  Supabase Cloud
       - auth.users (email/password, email verification)
       - public.user_profiles (roles, approval status)
       - public.Assets (information assets and risk data)
       - public.AssetControls (which of 13 controls apply per asset)
       - public.SystemLogs (audit trail)
       - public.ReportData (reporting metadata)
       - Row Level Security (RLS) enforces role boundaries at database level

2.2 Technology stack

  Component          Technology
  -----------------  ----------------------------------------------------------
  User interface     index.html + assets/styles/main.css
  Application logic  assets/scripts/app.js (single file, ~3200+ lines)
  Database / Auth    Supabase (PostgreSQL + Supabase Auth)
  Excel export       ExcelJS (assets/vendor/exceljs.min.js)
  API client         Supabase JS (assets/vendor/supabase.min.js)
  Dev server         Node.js scripts/serve.mjs (port 8000, static files)
  Package manager    npm (package.json)

2.3 Design principles

  - Standards-first: Risk math and control mapping cite real framework IDs.
  - Defense in depth: Residual risk reduced only by threat-relevant controls, with synergy bonuses.
  - Non-bypassable floors: Missing mandatory controls raise residual risk floor.
  - Auditability: Every approve, reject, delete, and submit writes to SystemLogs.
  - Role separation: UI filtering plus database RLS (defense in depth).

3. WEBSITE STRUCTURE AND SCREENS
================================================================================

3.1 Authentication (pre-login)

  - Login: Email and password via Supabase Auth.
  - Register: New users request a role (Standard User or Info Sec); account stays
    pending until approved by Info Sec or Admin.
  - Email verification: Supabase sends confirmation link; user must verify before
    full access (unless manually confirmed in Supabase Dashboard).
  - Pending approval screen: Shown when account_status is pending.
  - Rejected account screen: Shown when account was rejected; displays reason and
    option to return to login/register.

3.2 Main application sections (post-login, role-dependent)

  Section              Who can access          Purpose
  -------------------  ----------------------  ------------------------------------
  Dashboard            Info Sec, Admin         Risk posture KPIs, register charts
  Add Asset            All roles               Create new asset (starts as Draft)
  My Submissions       User, Info Sec          User's own draft/pending items
  Draft Queue          Info Sec                Review user-submitted drafts
  Asset Approval       Admin                   Approve/reject Pending assets
  Account Approvals    Info Sec, Admin         Approve/reject user registrations
  Asset Table          Info Sec, Admin         Full register listing
  Risk Register        Info Sec, Admin         Risk-focused view + 5x5 heatmap
  Control Metrics      Info Sec, Admin         Bar chart of control adoption
  Action Plans         Info Sec, Admin         Treatment plans for elevated risks
  System Logs          Info Sec, Admin         Audit log with filters
  Reporting & Sign-offs Admin only            Report metadata + Excel export
  Risk Guidelines      All roles               Reference scales and methodology

3.3 Asset form structure (Add / Edit Asset)

  The asset form is divided into logical cards:

  A. Asset identification
     - Asset ID, name, type (IA, PhA, PA, SA, SV, FA), owner, host, environment, etc.

  B. Sensitivity and valuation (Info Sec / Admin only for full profiling)
     - PII, SPI, corporate confidential flags
     - Confidentiality, Integrity, Availability (C, I, A) scores (1-3 each)
     - CIA total and classification band (Public, Internal Use, Confidential, Restricted)

  C. Risk assessment and controls (Info Sec / Admin)
     - Threat category, risk description
     - Probability (1-5) and Severity (1-5)
     - Inherent and residual risk (computed live)
     - Thirteen security controls (checkboxes with relevance/mandatory states)

  D. Treatment and action plan
     - Treatment type: Mitigate, Transfer, Avoid, Accept (with restrictions)
     - Action plan text, status, owner, target date

================================================================================

4.1 Roles

  Role            Description
  --------------  ------------------------------------------------------------

  Info Sec        Profiles drafts, submits to CISO, manages users (Standard only)
  Admin (CISO)    Final asset approval, full dashboard, 10-sheet Excel export

4.2 Permission summary

  Capability                    User    Info Sec    Admin
  ----------------------------  ------  ----------  -----
  Add asset (Draft)             Yes     Yes         Yes
  Profile Draft (risk/controls) No      Yes         Yes
  Submit Pending to CISO        No      Yes         Yes
  Approve/Reject Pending asset  No      No          Yes
  Reject Draft                  No      Yes         Yes
  Delete asset (with reason)    No      Yes         Yes
  Approve Standard User account No      Yes         No
  Approve any user account      No      No          Yes
  Dashboard / Risk Register     No      Yes         Yes
  Excel export (7 sheets)       No      Yes         No
  Excel export (10 sheets)      No      No          Yes

4.3 Account approval workflow

  1. User registers and selects requested role.
  2. user_profiles row created (pending status).
  3. Info Sec approves Standard User requests; Admin approves Info Sec requests.
  4. On approval: account_status = active, approved_role set.
  5. On rejection: account_status = rejected, rejection_reason stored.

4.4 Enforcement layers

  Layer 1: JavaScript showSection() and CSS data-role attributes hide UI.
  Layer 2: Supabase Row Level Security blocks unauthorized database operations.

5. ASSET WORKFLOW (THREE-TIER)
================================================================================

  Standard User          Info Sec                 Admin (CISO)
       |                      |                         |
       v                      v                         v
    [Draft]  ------------>  enrich risk,        [Pending Approval]
    form fill               controls, submit           |
       |                      |                    approve / reject
       | reject               |                         v
       v                      v                   [Approved]
    [Deleted]            back to Draft
                         (with reason)

  Status values:
  - Draft: User submitted basic asset data; awaiting Info Sec profiling.
  - Pending Approval: Info Sec completed risk work; awaiting CISO decision.
  - Approved: In the official register; appears on Dashboard and exports.
  - Rejected: Removed from active workflow (with logged reason).

  Every transition writes a SystemLogs entry used for notifications and Excel audit.

7. RISK CALCULATION ENGINE
================================================================================

All live calculations run in calculateRiskMath() in assets/scripts/app.js when the
user edits probability, severity, threat, environment, CIA scores, or controls.

7.1 CIA classification

  CIA score = C + I + A (each 1-3, total 3-9)

  Score   Classification
  ----    ----------------
  3       Public
  4-5     Internal Use
  6-7     Confidential
  8-9     Restricted

7.2 Inherent risk (before controls)

  Step 1: Start with user-selected Probability (P, 1-5) and Severity (S, 1-5).

  Step 2: Apply inherent escalations (NIST SP 800-30 style):

  Condition                                          Effect
  -------------------------------------------------  -------------------------
  Internet Facing + cyber-external threat            P = min(5, P+1); P >= 3
  PII or SPI + data leak or DPA breach threat        S = 5
  CIA score >= 8 + cyber or insider threat           S = max(S, 4)
  Asset type FA (Financial) + cyber threat           S = 5
  (PCI-DSS cardholder data breach = maximum impact)

  Step 3: Look up inherent rating from 5x5 matrix INHERIT[S-P]:

  Ratings: Very Low, Low, Moderate, High
  (Matrix keys are severity-probability, e.g. "5-3" = High inherent)

7.3 Residual risk (after controls)

  Step 1: Determine threat-relevant controls from controlMap[threat].

  Step 2: Sum CONTROL_WEIGHTS for each checked, enabled, relevant control.
          Each control has weights {p, s} reducing probability and/or severity.

  Step 3: Add synergy bonuses when control pairs are both active, for example:
          - RBAC + MFA
          - Backup + IRP
          - EDR + Firewall
          - Encryption + Segmentation
          - Vulnerability mgmt + EDR + IRP

  Step 4: Apply diminishing returns (saturating curve):
          reduction = (score - 1) * (1 - exp(-rawSum / 2))
          Prevents checking many controls from driving score to 1 unrealistically.

  Step 5: residual P = max(1, round(P - pReduction))
          residual S = max(1, round(S - sReduction))
          Residual rating = INHERIT[residualS-residualP]

7.4 Mandatory control floors

  After computing residual, the engine checks mandatory baselines. If required
  controls are missing, residual cannot fall below the floor:

  Trigger              Required controls (IDs)           Floor
  -------------------  --------------------------------  ---------
  Restricted (CIA>=8)  RBAC, MFA, Backup, Encryption,  Moderate
                       IRP
  Confidential (6-7)   RBAC, Encryption, IRP             Moderate
  FA (PCI scope)       MFA, Encryption, Vuln, Segment    High
  PII or SPI           Procedures, RBAC, Backup, Enc     Moderate
  Internet Facing      Firewall, Vuln, IRP               Moderate

  Citations shown in UI: ISO 27001, NIST CSF, CIS v8, PCI-DSS, RA 10173, GDPR.

7.5 Risk appetite enforcement (treatment type)

  Accept is disabled when:
  - Residual = High (ISO 27001 risk appetite)
  - Asset type FA and residual not Low or Very Low (PCI-DSS)
  - CIA >= 8 and residual = Moderate (Restricted - CISO sign-off required)

7.6 Control picker states

  Each control checkbox is classified as:
  - Relevant: Lowers P/S for this threat
  - Compliance baseline: Required by floor but may not lower P/S for this threat
  - Both: Relevant and required
  - Disabled: Neither relevant nor required (cannot be checked)

8. DASHBOARD METRICS (RISK POSTURE)
================================================================================

All dashboard KPIs use APPROVED assets only (status = Approved).

8.1 Share >= Moderate residual (elevated)

  Elevated = residual is Moderate OR High
  Formula: (elevated count / total approved) * 100, rounded to 1 decimal

8.2 Assets at elevated residual

  Count = number of approved assets with Moderate or High residual.
  Subtitle: Average inherent tier across ALL approved assets:
    Very Low=1, Low=2, Moderate=3, High=4
    Average = sum of tiers / count with valid inherent rating

8.3 Risk register completeness (threat + P x S)

  Assessed = asset has non-empty riskDesc AND prob AND sev set
  Formula: (assessed / total approved) * 100

8.4 Response progress

  Scope: Elevated assets only (Moderate or High residual)
  Advancing = actionStatus is "In Progress" OR "Done"
  Formula: (advancing / elevated count) * 100
  Detail: "X of Y with treatment in flight or closed"

8.5 Register overview (additional dashboard cards)

  - Total approved assets
  - High residual count
  - Moderate residual count
  - Assets with PII or SPI

16. ONE-PARAGRAPH SUMMARY (FOR ABSTRACT OR INTRODUCTION)
================================================================================

ImpactLens is a multi-role web application for PLM's Information Security
Management System that digitizes the Information Asset Register and risk
assessment workflow. Built with vanilla JavaScript and Supabase, it enforces a
three-tier approval process (Draft, Pending Approval, Approved), role-based access
for Standard Users, Info Sec analysts, and the CISO, and a risk engine grounded
in NIST SP 800-30 with ISO/IEC 27005 concepts. Thirteen security controls are
cross-mapped to NIST CSF 2.0, ISO 27001:2022, CIS v8, SOC 2, and PCI-DSS v4.0,
with mandatory floors under RA 10173, ISO 27701, and GDPR Article 32 for
privacy-sensitive assets. Residual risk uses weighted defense-in-depth reduction,
synergy bonuses, and diminishing returns, while treatment options respect ISO 27001
risk appetite rules. The platform provides dashboard analytics, compliance gap
analysis, system audit logs, and a seven-to-ten-sheet Excel export suitable for
ISMS documentation and CISO sign-off.
